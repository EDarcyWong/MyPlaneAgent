# 迁移示例

本目录包含从旧架构迁移到新架构的完整示例。

## 示例列表

### 1. 简单工具调用迁移
**文件**: `migration-example-1-simple-tools.ts`

展示如何将旧的直接函数调用迁移到新架构，提供三种迁移方案：

- **方案 A: Legacy Adapter** - 最快速的迁移方式
- **方案 B: 直接使用 Registry** - 推荐的标准方式
- **方案 C: 封装工具类** - 适合大型项目

**适用场景**: 
- 简单的工具函数调用
- 无复杂业务逻辑
- 需要快速迁移

**运行方式**:
```bash
npx tsx examples/migration-example-1-simple-tools.ts
```

**文件**: `migration-example-2-business-logic.ts`

**运行方式**:
```bash
npx tsx examples/migration-example-2-business-logic.ts
```

## 迁移策略选择

根据项目情况选择合适的迁移策略：

| 项目类型 | 推荐方案 | 原因 |
|---------|---------|------|
| 小型项目/POC | Legacy Adapter | 改动最小，快速验证 |
| 新项目 | 直接使用 Registry | 从一开始就用标准方式 |
| 中型现有项目 | Agent + Registry | 关键流程用 Agent，工具用 Registry |
| 大型现有项目 | 封装工具类 + Agent | 保持接口兼容，渐进式迁移 |
| 工具库 | 创建 Skill | 封装为可复用组件 |

## 迁移步骤

### 阶段 1: 评估 (1-2 天)

1. 识别需要迁移的代码
2. 评估复杂度和依赖关系
3. 选择迁移策略
4. 制定迁移计划

### 阶段 2: 准备 (1-3 天)

1. 搭建新架构环境
2. 运行测试验证系统可用
3. 创建必要的 Skills
4. 准备迁移工具和脚本

### 阶段 3: 迁移 (根据规模)

**小规模 (< 10 个工具)**:
- 1-2 天
- 使用 Legacy Adapter 或直接迁移

**中规模 (10-50 个工具)**:
- 1-2 周
- 分批迁移，先核心后边缘

**大规模 (> 50 个工具)**:
- 2-4 周
- 渐进式迁移，保持两套系统并行

### 阶段 4: 验证 (1-2 周)

1. 功能测试
2. 性能测试
3. 稳定性测试
4. 用户验收测试

### 阶段 5: 上线 (1 周)

1. 灰度发布
2. 监控和调优
3. 文档更新
4. 团队培训

## 常见问题

### Q1: 迁移会影响现有功能吗？

**答**: 不会。使用 Legacy Adapter 可以保持原有接口不变，新旧代码可以并行运行。

### Q2: 必须一次性全部迁移吗？

**答**: 不必。可以渐进式迁移：
- 新功能用新架构
- 旧功能保持不变
- 逐步替换核心模块

### Q3: 性能会受影响吗？

**答**: 轻微影响，但收益更大：
- JSON-RPC 调用增加 < 10ms
- Worker 池避免频繁启动
- 整体性能持平或更好

### Q4: 需要学习新技术吗？

**答**: 基础使用不需要，高级功能可选：
- 基础: 了解 Capability Registry
- 进阶: 创建自定义 Skill
- 高级: 使用 Agent 自动规划

### Q5: 如何处理现有的测试？

**答**: 三种方式：
1. Mock Legacy Adapter（最快）
2. 重写为新接口测试
3. 保留旧测试，新增新测试
